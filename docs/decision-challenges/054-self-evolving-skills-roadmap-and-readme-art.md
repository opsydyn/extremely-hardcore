# Decision challenge: self-evolving skills roadmap and README art

## trigger

The user asked to treat self-evolving skills as a possible moat. This triggers
the product-differentiation rubric. The approved slice records a roadmap
hypothesis and adds a static README asset; it does not build or compare the
capability.

## proposal and claims

Extend the existing governed skill-evolution backlog with a staged hypothesis:
bounded candidate skill changes, independent held-out evaluation, critical
regression checks, human promotion, and retained evidence could become a
compounding differentiator for EHS. Add the supplied artwork to the README.

The roadmap must not claim that this moat exists today. It claims only that
the hypothesis is worth preserving as a gated initiative and that evidence is
required before promotion or competitive language.

## existing-platform ownership

- Coding-agent hosts own execution sessions and their built-in model/tool
  behaviour.
- An external optimiser may own candidate proposal if used later.
- EHS owns the engineering method, protected governance skills, evaluation
  evidence, promotion boundary, and human-readable record of decisions.
- The README owns presentation, not capability proof.

## durable differentiated value

The possible value is a closed learning loop around engineering behaviour:
changes to skills are treated as untrusted proposals, tested against
independent evidence, and adopted only through a human-controlled gate. That
could compound without making EHS depend on one provider or optimiser, but it
is not differentiated value until repeated held-out results show it.

## strongest counterargument

Self-evolution can overfit the evaluator, encode accidental policy, increase
attack surface, and create a false sense of a moat. Existing optimisers or
agent platforms may already offer candidate generation. The roadmap therefore
keeps the initiative backlogged, protects the evaluator and governance skills,
requires independent holdouts and critical-regression checks, and forbids
autonomous adoption.

## claim-to-evidence map

| Claim | Current evidence | Gap | Required evidence |
| --- | --- | --- | --- |
| EHS has a governed skill-evolution initiative | Existing roadmap section and Run 054 update | No implementation exists | Future sandbox and promotion record |
| Self-evolving skills could be a moat | Product hypothesis only | No longitudinal or comparative result | Repeated held-out improvements without critical regressions |
| Human promotion is required | Existing roadmap guardrails | No promotion workflow is implemented | Future independent review and approval record |
| README artwork is included | Supplied local JPEG, copied and hash-checked | Visual branding proves no capability | Asset-integrity and README-reference checks |

## minimum credible slice

Record the hypothesis and its gates in the existing roadmap, add the supplied
image to the README, and verify both without implementing self-evolution.

## stop conditions

- Stop if roadmap wording becomes a present-tense moat or performance claim.
- Stop if the work starts generating, evaluating, or adopting candidates.
- Stop if an optimiser, provider, network, or writable execution boundary is
  introduced.
- Stop if the image must be altered or fetched from an external source.

## verdict

proceed

## rationale

The user has approved a narrow roadmap and presentation change. The proposal
preserves a potentially valuable direction while making its evidence burden
and security boundary explicit. Implementation remains separately gated.
