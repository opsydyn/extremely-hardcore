# decision challenge: operational acceptance and current host matrix

## trigger

This slice updates public roadmap and provider-onboarding claims and records
current host boundaries. It could be mistaken for a provider comparison or a
release decision, so the challenge must keep it as an evidence review rather
than an execution or benchmark feature.

## proposal and claims

- Aggregate Runs 1 through 10 as the core operating sample and report Runs 11
  and 12 separately as targeted supplemental dogfood.
- Report documented acceptance coverage, evidence-path retention, friction,
  false-block field coverage, timing, and fresh-agent readability with their
  actual denominators and gaps.
- Refresh current Codex, Claude Code, and Pi version and loading states.
- Keep release and provider expansion open where direct evidence is blocked or
  not retained.

These claims are about repository records and disposable local host checks.
They do not claim provider quality, adherence, isolation, containment, or
publication readiness.

## existing-platform ownership

Codex, Claude Code, and Pi own their own authentication, session lifecycle,
provider traffic, and host discovery mechanics. EHS owns the standalone
engineering method, onboarding instructions, local protocol, and the limits of
its evidence claims. This slice adds no host adapter or orchestration layer.

## durable differentiated value

The durable value is disciplined separation of evidence classes: a retained
protocol run is not the same as an attestation projection, a package install is
not a model-loading smoke, and a loading smoke is not engineering adherence.
The aggregate makes those boundaries visible before release claims are made.

## strongest counterargument

An aggregate review may create the appearance of progress without adding a new
external engineering task, while missing historical projections and
unstandardized fields prevent a clean operational metric. The appropriate
response is to record the incompleteness and hold the release decision, not to
invent a rate or expand into provider execution.

## claim-to-evidence map

| Claim | Current evidence | Gap | Required treatment |
| --- | --- | --- | --- |
| The core campaign is complete as a set of records | Ten records 033 through 042 exist; all report final protocol validation | This is not a fresh rerun of every target | Report as documented historical coverage |
| Core acceptance coverage is 65/65 | Run result tables and criterion-linked run files | Historical claims are not a new independent qualification | Label as record-reported, not a benchmark |
| Evidence paths are retained | Host path audit found all run, evidence, and log paths | Three core attestation/CI projections are missing | Report retention gap explicitly |

| Current hosts load EHS | Codex discovery, Claude metadata, Pi auth/loading checks | Codex and Claude model smokes are blocked | Mark Pi loading verified; keep the others pending |
| EHS is release-ready | None of the above proves release, adherence, or containment | Release gates remain open | Keep release on hold for review |

## minimum credible slice

Complete the aggregate, refresh the matrix with disposable commands, update the
narrow documentation surfaces, and validate the new records. Do not add a
metric collector, provider adapter, benchmark runner, or writable execution
path.

## stop conditions

- A result cannot be labeled as host-captured, record-reported, or unavailable.
- A model smoke requires storing credentials or raw provider output.
- The aggregate would need a false-block or readability denominator that the
  records do not contain.
- Documentation changes imply a compatibility, performance, isolation, or
  release guarantee.

## verdict

proceed

## rationale

The review is the next bounded roadmap item, and it reduces claim risk without
adding machinery. Its correct outcome may be a release hold; that is useful
evidence rather than a failed implementation.
